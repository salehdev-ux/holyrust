| Q1 | **Spec conflict:** §2.2D names Cranelift as the backend, but §1.1(3) demands "no external dependencies, one small self-contained compiler" and Principle 5 demands self-containment. Cranelift is a ~60-crate dependency tree. | DEGRADE per Part 4 Stage 5: self-contained direct x86-64 emitter + mmap (the spec's own fallback family, minus the `cc` subprocess). See DECISIONS D003. | RESOLVED (DEGRADE, logged). Human review welcome. |
| Q2 | L8 requires move/borrow semantics but the spec fixes **no syntax** for references/borrows. | HolyC pointer syntax, Rust semantics: `T *p = &x;` shared, `&mut x` exclusive, `*p` deref, lexical release. D009. | RESOLVED (documented in LANG_SPEC §7). |
| Q3 | L5/L8 imply strings; no string type is specified (L1 lists only scalars). | Built-in `Str` support type (heap block + ownership header; immortal literals). D007. | RESOLVED (LANG_SPEC §3). |
| Q4 | Component E lists "(ownership tracker, allocator, **doc/graphics**)" in the §2.1 diagram, but §2.2E text mandates only "minimal print/alloc/free builtins" and the frozen table L1–L11 has no graphics. | Diagram text treated as illustrative; graphics builtins OUT of v1 (quarantined in FUTURE_IDEAS). §2.2E text + frozen table win (they are normative). | RESOLVED (scope-limited). |
| Q5 | **Phase 6 blocker (anticipated):** `qemu-system-x86_64` absent from the build environment; real-kernel exit criteria (boot <5s, scripted QEMU session in CI) unverifiable here. | SPEC Phase 6 risk note sanctions a **host-side hot-patch simulation** as an acceptable v1 deliverable. Plan: deliver simulation first (D016); attempt apt-installed QEMU + minimal boot afterwards only if schedule allows, never at the cost of the simulation. | RESOLVED (v1, BOTH tracks): Phase 6 delivered first as the spec-sanctioned host-side simulation (D016/D037, `demos/kernel_sim.hr`, CI test `kernel_sim`), then — because the simulation landed early and QEMU proved installable — as a REAL bootable kernel (P6b, D038–D042): multiboot → long mode → in-kernel compiler → live `KbdEcho` hot-patch with post-edit `HeapCheck()` — scripted QEMU session in CI (`tools/kernel_ci.py`, `tests/kernel_boot.rs`, boot 0.16s vs <5s gate). Remaining kernel gaps honestly open: IRQ/IDT keyboard interrupts (F16), SMP, UEFI, W^X hardening (F6 rewritten accordingly). |
| Q6 | L3 variadics: semantics of `argc/argv` when named params precede `...`, and how F64 args appear in `argv`. | `argc`/`argv` cover ALL passed args (named + variadic); `argv[i]` is the I64 view of the 8-byte slot; F64-in-variadic visible only as raw bits in v1. | Q9 | Part 5 item 8: "No `unwrap()` on user-controlled input paths" — scope of "user-controlled" (test fixtures? | Q10 | **Delivery conflict (TempleOS-RS Phase 0):** v1 is declared x86-64-**Linux**-only (§1.3; "the JIT emits x86-64 machine code and uses Linux `mmap` semantics"), and INSTALL.md directs Windows users to WSL2. But the owner's machine is Windows 10 with **no WSL distro, no in-process elevation and 4 GB RAM**, so the documented path requires an elevated `wsl --install` **and a reboot** before anything can be compiled. Is the "Linux-only" clause a *language* constraint or a *platform* constraint? | Read it as a **platform/ABI** statement, not a semantic one: the JIT's real contract is "x86-64 machine code following the SysV ABI", and nothing about ownership, hot-patching or the compiler depends on Linux. So the owner was offered the choice — enable WSL2 (spec-exact, needs the reboot) or port the host (**no reboot, no admin**) — and chose the port. Recorded as D043 (host) + D044 (kernel build/CI); the Linux path is preserved unchanged (`code_mem` keeps `mmap`/`mprotect` verbatim, `extern "sysv64"` *is* `extern "C"` on Linux, `build.sh` untouched). | RESOLVED (port delivered; 97/97 tests + `KERNEL-CI: PASS` on the native Windows host). §1.3's "x86-64 only" still holds — the *target* architecture never changed. |
| Q11 | **SPEC_TOS.md Phase 0 Task 2 vs. Part 6:** the task says "Create `docs/SPEC_TOS.md` (this document)", while Part 6 lists `SPEC_TOS.md` as the SSOT — but the repository already had a `SPEC.md` (the HolyRust **v1** build spec) at its root. Two documents, one name collision. | Kept both, with explicit scopes: `SPEC.md` remains the SSOT for **HolyRust v1** (compiler, language, P6b kernel) and `docs/SPEC_TOS.md` is the SSOT for the **TempleOS-RS** build, cross-referenced in a provenance note at its head. Nothing in v1 was overwritten, so no v1 gate loses its normative reference. | RESOLVED (both docs present and cross-linked). |
| Q12 | **Is the following a v1 defect?** A `Str` **variable** is consumed when passed to a user-defined function (consistent with D008 move semantics — accepting that as *by design*), but a `Str` **pointer/borrow parameter** (`I64 G(Str *p) { return StrLen(*p); }` called as `G(&v)`) terminates the process with `0xC0000005` (access violation) instead of a diagnostic, and produces no output at all. Reported while writing `/TOS/Files.HR` (PROGRESS TOS-P1.2 #3). | Treated as a **real defect, not a design choice**: the project's own thesis is "diagnostics over crashes" (Part 7.5), and every other guest mistake in v1 produces a positioned runtime diagnostic that leaves the session alive. Not fixed in Phase 1 — it is outside the filesystem's scope and the FS layer is written to avoid borrows entirely (documented in `/TOS/Files.HR`'s header). Safe workaround adopted: never take a `&` of a `Str` in TOS code. | **OPEN** — needs a dedicated fix + regression test; belongs in the HolyRust (v1) bug list, not the TempleOS-RS phase plan. |
| Q13 | **Where exactly does T1.4's "command processor" end?** The task says `/TOS/Shell.HR` "replaces the C-era `hr_shell`", but a shell cannot read its own input or compile itself without the host loop. | Split by *policy*, not by file: reading a line and invoking the JIT stay in Rust (that is what a JIT host is), while every command name, argument rule and message moved to `/TOS/Shell.HR`; the kernel decides only *lexically* whether a line is a bare command word. See D046. | RESOLVED (D046; unquoted argument form quarantined to F18). |
